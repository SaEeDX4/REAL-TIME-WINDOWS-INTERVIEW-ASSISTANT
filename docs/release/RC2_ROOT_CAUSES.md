# 2.1.0-rc.2 — root-cause analysis

Every row was traced in the 2.1.0-rc.1 code (build `5ce6b95`) **before** the fix was written, and each
fix has a regression test. Test names refer to `tests/InterviewAssistant.Tests` unless stated otherwise.

| # | Symptom (RC1 manual testing) | Root cause (traced in code) | Fix | Regression tests |

| 1 | A Windows beep or a screenshot sound produced a "question" that read like the transcription vocabulary ("Job interview for … Terms: …") and got an answer | Two independent defects. (a) The engine forwarded every server-VAD segment to the turn detector with **no evidence that speech was present**: a tone or a click that crosses the VAD threshold is segmented like speech. (b) The realtime transcription model, given a non-speech segment, often returns **its own bias prompt** (or "Thank you.") as the transcript. Nothing downstream recognised either case. | Defence in depth: `AcousticAnalyzer` measures voiced (periodic, pitch-range) and tonal (1–2 spectral peaks) time for every audio frame; `SpeechEvidenceTimeline` attributes evidence to each VAD segment; `PromptEchoDetector` recognises the prompt vocabulary, the "Terms:" marker and long runs copied from the prompt; `UtteranceGate` vetoes non-speech, short acoustic events, echoes and noise, both per turn and **per segment** (so an echo can never merge into the next real question). ## Diarization

Speaker diarization was evaluated and **not** used for RC2. OpenAI documents `gpt-4o-transcribe-diarize`
for the (non-realtime) Transcription API; realtime availability is unclear and developers report errors
when enabling it for realtime transcription
([model page](https://developers.openai.com/api/docs/models/gpt-4o-transcribe-diarize),
[community thread](https://community.openai.com/t/how-to-enable-gpt-4o-transcribe-diarize-for-realtime-transcription/1373561)).
The product therefore does **not** claim to know who is speaking. It uses the conservative directedness
rules in row 5 and never stores speaker biometrics.
